# OCR v7 开发交接包

## 1. 先看这三件事

这是一个“商品图片识别并生成运营 Excel”的 Windows 本地应用，不是单纯 OCR 工具。

输入是一批按商品 ID 分文件夹存放的包装图片。系统先读图片文字和数据库商品资料，再由 Qwen 生成结构化商品/运营字段，最后导出 Excel、CSV 和审计报告。

开发时最重要的不是“让程序跑完”，而是保证：

1. 不把模型猜测当成商品事实；
2. 不把不同平台、不同商品的数据库数据混在一起；
3. 图片或数据库异常时保留已成功数据，并明确标记待复核；
4. Excel 每一列都可追溯到图片、数据库、模型或公式。

## 2. 业务对象和输入

### 2.1 一个商品是什么

- 商品目录名称：`platform_goods_id`。
- 业务上 `platform_goods_id`、`product_id`、`item_id` 都是“官方平台商品 ID”的同一概念。
- 系统内唯一身份：`(platform, product_id)`，例如 `(jd, 1869569)`。
- `platform_goods_key` 是数据库内部关联键，不等于图片文件夹名；它要先从商品主表或月度表取得。

### 2.2 图片目录格式

```text
<平台>\
  <批次目录>\                 <- 在前端选择这里
    <platform_goods_id>\
      01.jpg
      02.jpg
```

支持图片格式：`jpg/jpeg/png/webp/bmp/tif/tiff`。一次 GUI 运行选择 1 到 100 个商品；约 10,000 商品应使用批量首轮模式和批量任务工具。

## 3. 用户实际得到什么

每次运行生成 `runs/<run_id>/`：

| 文件                     | 给谁看     | 用途                                   |
| ---------------------- | ------- | ------------------------------------ |
| `result.xlsx`          | 业务用户    | 主结果；`Result` 是商品结果，`Audit` 是追溯/错误/来源 |
| `result.csv`           | 数据使用者   | 主结果的 CSV 版本                          |
| `products/<商品ID>.json` | 开发和复核人员 | 单商品完整字段、来源与校验问题                      |
| `待复核图片.json`           | 人工复核人员  | OCR 未成功图片和错误原因                       |
| `实时结果.html`            | 运行中的用户  | 已完成商品的阶段性输出                          |
| `report.html`          | 业务和开发人员 | 运行结果、失败原因、性能统计                       |
| `performance.json`     | 开发人员    | 阶段耗时、OCR P50/P95、吞吐、缓存和历史对比          |

`review` 不是“没有结果”。它表示系统已经输出可用部分，但至少有一张图片、一个字段或一项校验需要人工确认。

## 4. 固定业务流程

```text
图片目录
  -> manifest（平台、商品 ID、图片路径、SHA256）
  -> PostgreSQL 查询 和 Paddle OCR 并行
  -> 已完成 OCR 的商品可进入 Qwen 提取
  -> 业务校验
  -> Excel / CSV / JSON / HTML
```

### 4.1 OCR 阶段

内网 PaddleOCR-VL 接口为 `/v1/ocr`。程序每批最多发送 8 张图，GUI 允许 1 或 2 批并行。OCR 成功内容按“图片 SHA256 + 模型版本”缓存；恢复同一运行不会重发成功图片。

单张图请求慢或失败时，不应阻塞同商品其他已成功图片，也不应阻塞后续商品。失败图片标记为待复核，成功图片继续供 Qwen 使用。

### 4.2 数据库阶段

PostgreSQL 与 OCR 同时开始。数据库失败不能清除已经完成的 OCR 产物，但没有数据库快照时，正式结果不能伪造价格或属性。

### 4.3 Qwen 阶段

Qwen 接收：商品名称、该商品的 OCR 文本、数据库属性。它返回严格 JSON，字段定义在 `template-v2.json`。

普通模式下，缺失的生产信息可以触发联网搜索；批量首轮模式跳过联网搜索，仅生成核心识别结果和待补全字段。

### 4.4 校验与导出

系统汇总各来源、计算规格价格/日服成本，并对冲突或污染图片打标。最后写入商品 JSON、CSV、Excel 和报告。

## 5. 数据库契约

### 5.1 表、键和职责

| 对象                                                        | 查询条件                 | 主要用途                       | 重要规则            |
| --------------------------------------------------------- | -------------------- | -------------------------- | --------------- |
| `workdb.d_platform_goods`                                 | `platform_goods_id`  | 商品主表、内部 key、商品名、店铺、品牌、主表价格 | 首先查询            |
| `workdb.mv_com_goods_statistics_monthly_v2_internal_ssv4` | `platform_goods_id`  | SSV4 月度商品名和月度价格            | 价格的优先来源，可能是普通视图 |
| `workdb.d_platform_goods_attributes`                      | `platform_goods_key` | SSV4 属性                    | 必须在获得内部 key 后查询 |
| `workdb.new_infinitus_attribute`                          | `item_id`            | 无限极属性补充                    | 只补 SSV4 缺失的同名属性 |

当前程序查询顺序如下：

```text
商品 ID
  -> 商品主表 + 月度 SSV4 表（均按 platform_goods_id）
  -> 从两个结果收集 platform_goods_key
  -> SSV4 属性表（按 platform_goods_key）
  -> 无限极属性表（按 item_id）
```

### 5.2 合并与优先级

- SSV4 属性优先，无限极属性只补缺失字段。
- 月度价格在可唯一确认时优先；否则使用主表价格；不能确认时价格为空并写校验问题。
- 如果数据库表没有平台字段，系统必须保留 `PLATFORM_UNVERIFIED`，不能假定同 ID 跨平台一定相同。
- 月度对象和 SSV4 属性表当前单次查询上限为 300 秒。超时属于数据库问题，不是 OCR 问题。

### 5.3 DBA 需要确认的事项

新人拿到代码前，DBA/数据负责人必须提供：

1. 四个对象的实际 schema、列类型和是否含平台字段；
2. 月度对象是普通表、物化视图还是普通视图；
3. 至少一个可用的只读测试账号及测试数据；
4. 视图底层表的执行计划与索引责任人；
5. 是否已完成并分析以下查询索引：主表 `platform_goods_id`、属性表 `platform_goods_key`、月度底层表 `platform_goods_id`。

任何人都不应把 PostgreSQL 密码写入代码、README、Git、截图或聊天记录。

## 6. 结果字段和正确性规则

完整字段定义和类型在 `template-v2.json`。开发者修改字段前必须同步修改：模板、导出、审计、测试样本和业务验收表。

### 6.1 来源固定的字段

| Excel 列      | 允许来源                | 不允许做法         |
| ------------ | ------------------- | ------------- |
| `product_id` | 输入目录名               | 由模型改写         |
| `商品名称`       | 数据库商品名              | 从图片猜测后覆盖数据库   |
| `价格`         | 数据库月度价格或主表价格        | 由 OCR/Qwen 生成 |
| `品牌`         | 数据库属性优先，OCR/Qwen 补充 | 无证据猜测品牌       |
| `剂型`、`蓝帽标识`  | 数据库属性优先，OCR/Qwen 补充 | 没有文字证据时填充     |

### 6.2 事实字段的强制证据规则

以下四列的优先级固定，不能因为“看起来合理”而改写：

```text
图片 OCR 中明确出现的文字
  -> 数据库属性同义字段
  -> 带提供方 URL 的联网搜索结果
  -> 空值并进入待复核
```

字段为：`代工厂`、`代工厂地址`、`生产许可证`、`产地`。

Qwen 只能从 OCR 明确文本提取第一层证据；数据库或搜索回退由程序的确定性逻辑处理。没有 URL 的搜索答案不能作为事实写入。

### 6.3 公式字段

| Excel 列   | 计算规则                     |
| --------- | ------------------------ |
| `规格`、`包装` | 从 Qwen 的 `guige` 按程序规则拆分 |
| `规格总量`    | 优先解析规格，无法解析时使用模型明确返回的总量  |
| `最小单位价格`  | 价格 ÷ 规格总量；分母缺失或非正数则为空    |
| `最小日服成本`  | 价格、规格总量、最小日服量均有效时计算      |
| `最大日服成本`  | 价格、规格总量、最大日服量均有效时计算      |

### 6.4 必须标记待复核的典型情况

- 图片 OCR 未成功或超过时间上限；
- 同一商品识别到冲突的“每日”用量：`DOSAGE_CONFLICT`；
- 图片疑似竞争品、非本商品或品牌混入：`IMAGE_PRODUCT_MISMATCH`；
- 数据库商品身份、内部 key 或价格有歧义；
- 关键事实字段没有任何可验证来源；
- Qwen 输出不符合模板 JSON 类型/字段约束。

### 7.2 本机启动

双击 `启动OCR_Demo.cmd`。首次运行会建立 `.venv` 并安装 `psycopg`、`openpyxl`、`Pillow`。GUI 会记住非敏感配置，并用 Windows 加密保存凭据。

若开启 VPN 后 Paddle 地址不可达，管理员运行 `修复Paddle路由.cmd`，只有看到 `TcpTestSucceeded : True` 才继续。

开发自检：

```powershell
.\run_demo.ps1 -SelfTest
```

模拟工作流：

```powershell
.\run_demo.ps1 -Mock -Platform jd
```

真实测试：在 GUI 选择包含 5 个商品目录的批次，确认外发告知后运行。不要用生产密钥做大量重复性能测试。

## 8. 模块地图

| 文件                                | 新人应该知道什么                                                    |
| --------------------------------- | ----------------------------------------------------------- |
| `demo.py`                         | 主流程。入口 `main`，编排入口 `execute_pipeline`，OCR/数据库/Qwen/导出全部由它调度 |
| `paddle_ocr.py`                   | Paddle `/v1/ocr` 请求与返回结果校验；修改接口协议先改这里并补测试                   |
| `redshift_backend.py`             | 数据库对象发现、参数化小范围查询、属性和价格合并；不要在 GUI 里拼 SQL                     |
| `直接用图片测试.py`                      | Tkinter 前端、凭据 DPAPI 加密、子进程启动和日志显示                           |
| `template-v2.json`                | Qwen JSON 合同和 Excel 列定义；这是业务字段的单一事实来源                       |
| `batch_jobs.py`、`batch_worker.py` | 大批次串行任务与状态保存                                                |
| `retry_review.py`                 | 失败图片重试与缺失字段合并                                               |
| `test_*.py`                       | 现有行为基线；修改逻辑前先跑相关测试                                          |

## 9. 第一次开发的推荐步骤

1. 从 GitHub 克隆仓库，用 GitHub Desktop 确认 `main` 与远端一致。
2. 先运行 `-SelfTest`，不配置任何真实 Key 或数据库。
3. 阅读 `README.md`、`docs/OCR_v7_技术备份与交接说明.md` 和本文件。
4. 用 `-Mock` 查看完整输出结构，再用 5 个真实商品进行小范围验证。
5. 每次改动先创建分支，不直接修改 `main`；修改后运行相关 `test_*.py` 与一轮模拟测试。
6. 对字段、数据库映射、提示词或导出规则的任何改动，都必须使用同一批验收样本比较 Excel 差异。
7. 经业务负责人确认后再合并到 `main` 并推送。

## 10. 验收包必须由业务方补齐

代码仓库不能包含真实商品图片、生产账号或真实运行结果。因此，新人若要独立判断业务正确性，业务负责人必须单独提供下列验收包：

| 必需交付物    | 最低要求                                       |
| -------- | ------------------------------------------ |
| 图片样本     | 5 个商品，每个保留全部图片；至少包含一张文字清晰图、一张复杂包装图和一张应待复核图 |
| 期望 Excel | 每个样本关键列的人工确认值；允许为空的列必须显式标注“允许为空”           |
| 数据库快照    | 这 5 个商品在四个对象中的脱敏查询结果，含价格与属性来源              |
| 判定说明     | 为什么某字段应来自 OCR、数据库、搜索或留空                    |
| 性能基线     | 每张 OCR 的 P50/P95、整批耗时、成功率和运行日期/模型版本        |

没有这些验收材料时，新人只能证明“软件能运行”，不能证明“Excel 业务正确”。

## 11. 当前已知风险和禁止事项

- PostgreSQL 月度对象曾出现 300 秒超时；不要通过跳过月度对象来伪造完整结果，应先排查视图底层索引和执行计划。
- Excel 打开 `result.csv` 或 `result.xlsx` 时会阻止覆盖写入；关闭占用文件后恢复运行。
- Paddle、VPN、PostgreSQL 和 Qwen 是外部依赖；它们慢不会因为拆成 AI 子 agent 而变快。
- 不允许关闭 TLS 校验来“解决”连接问题，除非 DBA 明确说明该内网服务不支持 SSL，并在配置中显式记录。
- 不允许把 API Key、数据库密码、图片 Base64、完整连接串提交到 GitHub。
- 不允许在没有业务验收样本的情况下大改 `template-v2.json` 的字段含义或来源优先级。

## 12. 交接完成标准

以下全部完成，才算可以独立维护：

- 能在新电脑完成本地自检、模拟运行和 5 商品真实测试；
- 能解释四张数据库对象分别按什么键查询；
- 能解释“代工厂/地址/许可证/产地”为何不能由模型猜测；
- 能从 `report.html`、`performance.json` 和商品 JSON 找到一次失败的原因；
- 能修改一个非业务字段并通过自动化测试；
- 能在 GitHub Desktop 创建分支、提交、推送和发起代码评审；
- 业务负责人已签字确认 5 商品期望 Excel 与程序输出差异。
